Set up

Start here

The easiest path is the on-device Setup Wizard.

A fresh boombox auto-launches a first-run Setup Wizard on the touchscreen. Work through it right on the 5-inch screen, or scan the QR code it shows to continue from your phone or laptop browser — handy for typing Wi-Fi passwords and server URLs on a real keyboard. The wizard writes the same configuration this page documents, so anything it sets you can later inspect or change from the touchscreen Settings drawer.

The wizard walks through, in order:

Device name & Wi-Fi

Name the boombox and join it to your network so the rest of setup — and every remote — can reach it.

Music library

Connect your Navidrome (Subsonic) server: URL, username, password, tested live before it saves. Detailed below.

Video

Use the Jellyfin server bundled on the device, or point at your own server elsewhere. Detailed below.

Remotes

Enable the phone remote and pair your first device with a 6-digit PIN, or pair the CYD hardware remote.

Prefer to do it by hand, or need to change something after first-run? Every step has a manual equivalent — the sections below are the reference.

Music share

Mount the SMB share to move music on and off the boombox.

The installer publishes your music library as a read/write SMB share, so you can drag files in from Finder, Windows Explorer, or any SMB client instead of SSH. Editing files over the share changes the desktop user's ~/Music/ directory directly.

  • Share path — smb://<pi-ip>/boombox-music
  • Username — the desktop user (jwc on the current appliance).
  • Password — the same static remote credential used for the LAN web login. Read it with sudo cat /etc/boombox/web-auth.env; the touchscreen Settings drawer also shows it.

On macOS use Finder's Go → Connect to Server (⌘K) with the share URL. From a Linux box you can mount it read/write with cifs:

mount-share.sh 
# macOS — in Finder: Go → Connect to Server (⌘K)
smb://<pi-ip>/boombox-music

# Linux — mount read/write with the desktop user + web-auth password
sudo mkdir -p /mnt/boombox
sudo mount -t cifs //<pi-ip>/boombox-music /mnt/boombox \
    -o username=<desktop-user>,uid=$(id -u),gid=$(id -g)

After a big batch of adds, renames, or deletes, run a library scan from the touchscreen Settings drawer so Mopidy picks up the changes. The music share does not include ~/Videos/ — for video, use the upload button, a USB stick, or rsync (see the Video section).

Home library

Connect Navidrome for a browsable, offline-cached home library.

The Home Library is a parallel browse tree backed by a Navidrome — or any Subsonic-API-compatible — server on your LAN or a public host. Browse it from the touchscreen or PWA, pin albums to a USB cache drive for offline play, and stream the rest with one tap.

1. Configure the source

Open Settings → Home Library on the touchscreen (or the LAN web UI), fill in the fields, tap Test until you see ✓ Connected, then Save:

  • Source URL — http://<navidrome-host>:4533 (your own port works; https:// works too).
  • Username — your Navidrome user.
  • Password — your Navidrome password. It is Fernet-encrypted at rest with a key derived from the Pi's /etc/machine-id, so moving the SD card to another Pi makes it unreadable and forces re-entry.

The first full sync of a typical 5–10k-album library takes a few minutes and re-runs hourly. Auth uses Subsonic's token+salt scheme — a fresh salt per call, so your password never appears in a URL.

2. Adopt a USB cache drive

Plug in a USB stick formatted ext4 / NTFS / exFAT (FAT32 works but caps files at 4 GB). The kiosk pops a "New drive detected" overlay — tap YES, USE FOR CACHE and it writes a .boombox-cache marker, creates audio/, meta/, and tmp/ subdirs, and starts pulling any already-pinned tracks. You can also adopt a drive by hand:

adopt-cache.sh 
sudo touch /media/<drive>/.boombox-cache
sudo mkdir -p /media/<drive>/{audio,meta,tmp}
systemctl --user restart boombox-library

3. Browse & pin

Open the Library drawer, tap Home Library, and browse Artists / Albums / Playlists (all FTS-searchable) or the Cached only view. Tap the pin on an album, artist, or playlist and its tracks download to the cache drive — pinned content survives reboots, network failures, and the boombox going on a trip. Pinned albums play with no server reachable at all; everything else streams on demand, with a source badge on the now-playing bar (⬇ Cache · ⚡ Stream) telling you which pipeline is feeding the speakers.

Video

Play video from the bundled Jellyfin, or point at your own server.

A standalone Jellyfin server ships on the device, running on port 8096 independent of the music stack. You can leave it on-device or redirect the whole boombox — touchscreen included — at a server elsewhere. Both are single-setting choices.

On-device (default)

install.sh installs and configures Jellyfin against ~/Videos for you — no manual wizard. Tap WATCH in the Settings drawer and the kiosk opens http://localhost:8096/; a floating ← BOOMBOX pill returns you. Username is boombox; the password is the 6-digit number in /etc/boombox/web-auth.env. Any LAN browser or Jellyfin app can also point at http://<pi-ip>:8096/.

Off-device (your server)

Point BOOMBOX_JELLYFIN_BASE at your own Jellyfin and supply an API key. Every Jellyfin address on the boombox — the transport proxy, the WATCH button, and both library-refresh triggers — resolves through that one variable, so the whole device follows.

To redirect the device at an off-device Jellyfin, set the base URL and store an API key created in the remote server's Dashboard → API Keys, then restart the consumers:

jellyfin-offdevice.sh 
# 1. Point the device at your server (loaded by the units already)
echo 'BOOMBOX_JELLYFIN_BASE=https://video.example.com' \
    | sudo tee -a /etc/boombox/jellyfin.env

# 2. Store the API key from Jellyfin Dashboard → API Keys (single line)
printf '%s\n' 'PASTE_YOUR_JELLYFIN_API_KEY' \
    | sudo tee /etc/boombox/jellyfin-api-key >/dev/null
sudo chmod 0640 /etc/boombox/jellyfin-api-key

# 3. Restart the consumers so they pick up the new base + key
systemctl --user restart boombox-remote boombox-buttons

Jellyfin's default Movies library only indexes files named Title (Year).ext — e.g. Sintel (2010).mp4. For arbitrary files, switch the library to Mixed Content or add a second library of the right type. On a Pi 5, encode to H.264 / AAC for direct play; 4K / HDR forces a software transcode it can't keep up with.

Off-device servers

Run Navidrome + Jellyfin off the device, reachable from outside your home.

Moving both servers onto a real "home server" gives Jellyfin the CPU to transcode comfortably and puts your library state in one backed-up place. The boombox only ever needs a reachable HTTPS URL plus credentials for each server — it does not care where the box physically runs. The servers/ directory ships a Docker Compose stack for exactly this.

Bring it up (Docker)

Run it on any always-on box (a NAS, mini-PC, or old laptop is the recommended host — your media stays on your disks). Copy the example env, set your media paths and ports, and start it:

servers-up.sh 
cd servers
cp .env.example .env
$EDITOR .env          # set MUSIC_DIR, VIDEO_DIR, PUID/PGID, TZ, ports
docker compose up -d
docker compose ps     # both should show (healthy) within ~40 s

Then, once on the LAN, run each server's own first-launch wizard: open http://<host>:4533 to create the Navidrome admin, and http://<host>:8096 to create the Jellyfin admin and add a Movies library pointed at /media. Use strong, unique passwords — do not reuse the boombox's LAN credential.

Expose it from outside your home — pick one

The boombox needs an HTTPS URL it can reach. Both options below give you TLS; never expose either server as raw HTTP.

A · Cloudflare Tunnel

cloudflared dials out to Cloudflare, so you open no router ports and never reveal your home IP; Cloudflare terminates TLS at the edge. Create a tunnel in the Zero Trust dashboard, add public hostnames pointing at the navidrome / jellyfin service names, put the token in .env, and bring the stack up with the overlay. Strongly recommended: add a Cloudflare Access policy in front.

B · Port-forward + reverse proxy

If you'd rather not depend on Cloudflare, forward 443 (and 80 for the ACME challenge) to a reverse proxy on the host that terminates Let's Encrypt TLS. Caddy is the least-effort — automatic certificates. Forward only the proxy's ports, never 4533/8096 directly, and add rate-limiting at the proxy.

expose.sh 
# Option A — bring the stack up WITH the Cloudflare Tunnel sidecar
docker compose -f docker-compose.yml -f docker-compose.cloudflared.yml up -d

# Option B — a minimal Caddyfile (automatic Let's Encrypt TLS)
#   music.example.com {
#       reverse_proxy localhost:4533
#   }
#   video.example.com {
#       reverse_proxy localhost:8096
#   }

# Either way: tell Jellyfin its public origin, then re-up
echo 'JELLYFIN_PUBLISHED_URL=https://video.example.com' >> servers/.env

Then point the device at the public URLs: set Settings → Home Library Source URL to https://music.example.com, and BOOMBOX_JELLYFIN_BASE=https://video.example.com in /etc/boombox/jellyfin.env (see the Video section). Sync, streaming, and playback work the same off-LAN as at home.

Security is non-negotiable here. Exposing a media server is the highest-risk step in the project. Use strong, unique passwords, keep the servers patched (pin image versions and bump on a schedule), and add rate-limiting at the edge. A mesh VPN (Tailscale / WireGuard) or Cloudflare Access in front is safer than a bare public endpoint. Rule of thumb: mesh VPN > public + Cloudflare Access > public + reverse proxy with rate-limiting > raw port-forward (never). And back up the server state you can't re-copy — the navidrome-data and jellyfin-config volumes plus your .env:

backup.sh 
cd servers
docker compose stop            # quiesce for a consistent DB snapshot
docker run --rm \
  -v navidrome-data:/nd -v jellyfin-config:/jf \
  -v "$PWD":/backup alpine \
  tar czf /backup/boombox-servers-backup.tgz -C / nd jf
docker compose start

Remotes

Pair a phone PWA or the hardware remote.

The phone-facing surface is off by default — a privacy gate against arbitrary phones on the Wi-Fi. A human at the touchscreen has to turn it on before any phone route responds.

  • Open Settings → Phone remote on the touchscreen and flip ENABLE. The screen then shows a 6-digit pairing PIN (single-use, ~120-second lifetime, rotates freely).
  • On your phone, open the installable web app at http://<pi-ip>:8090/remote/ — the same URL the touchscreen's web-QR overlay encodes. Redeem the PIN to get a durable bearer token; use the browser's Add to Home Screen to install it as a standalone app.
  • The token survives reboots and is only revoked by unpairing from the touchscreen. Turning the toggle off later blocks phones but keeps paired tokens, so flipping it back on works without re-pairing.

The full LAN web UI lives at http://<pi-ip>:8090/ behind HTTP Basic auth — log in with the same credential from /etc/boombox/web-auth.env that the SMB share uses. (The /api/remote/ path is exempt from Basic auth because phones carry their own bearer tokens.) The CYD hardware remote uses the same backend over BLE and HTTP, so it keeps working regardless of the phone toggle.

This is a friction gate for a trusted LAN, not a hardened public-internet service: the credential is a short reused number, there's no rate-limiting, and traffic is plaintext HTTP. Don't enable the remote on a Wi-Fi network you don't trust, and never expose port 8090 to the internet.
